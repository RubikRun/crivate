# crivate v2.0 — Implementation Plan

v1.0 is the encrypt–view loop for one image at a time. v2.0 makes a folder of images usable as a private album: list names, add or delete several, browse a range in one window, change the folder password.

The application still never intentionally persists decoded image pixels as an image file. Drawing is still the averaged-square grid with 100 draw calls. The on-disk formats do not change.

---

## 1. Goal

A user can:

1. See each image’s index and filename after unlocking (`list`).
2. Add several images, or all images sitting directly in a directory, with one command.
3. View one image, a range, or the whole folder in a single viewer session, and step through that set with the A/D keys and wrapping on the first/last image.
4. Delete one image, a range, or all images (every `del` asks for confirmation first).
5. Change the folder password without exporting images.

If those five things work, and v1.0 behavior is still intact, v2.0 is done.

---



## 2. What v2.0 is — and is not



### In scope (the product)

v1.0 commands stay. New or extended commands:


| Command                         | Behavior                                                                                                                                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `crivate list`                  | Print each image’s 1-based index and `.cri` basename.                                                                                                                                    |
| `crivate add <path> [<path> …]` | Encrypt each file path, one unlock. A directory path adds the image files **directly inside it** (not recursive). Skip a dest `.cri` that already exists; do not overwrite, but do warn. |
| `crivate view`                  | Unlock once; view **all** images in one session.                                                                                                                                         |
| `crivate view {x}`              | Unchanged: one image.                                                                                                                                                                    |
| `crivate view {x} {y}`          | Unlock once; view that **inclusive** range in one session.                                                                                                                               |
| `crivate del`                   | Delete **all** `.cri` files after unlock and confirmation. `.crivate` remains.                                                                                                           |
| `crivate del {x}`               | Delete one image after unlock and confirmation.                                                                                                                                          |
| `crivate del {x} {y}`           | Delete that **inclusive** range after unlock and confirmation.                                                                                                                           |
| `crivate password`                | Change the folder password. Re-encrypt the verifier and every `.cri`. No image-file export.                                                                                              |


`init` and `count` are unchanged from the shipped v1.0 binary (`count` still prints the label line, then the number).

Every command except choosing a password on `init` / the new-password half of `password` still unlocks with the **current** folder password. There is no session unlock: each command prompts again.

Viewer, only while `view` is running:

- Same drawing rules as v1.0 (averaged squares, `W` / `S`, 100 draws, no image-file dumps, `Esc` or the close box exits).
- **A** or **Left**: previous image in the **current set**.
- **D** or **Right**: next image in the **current set**.
- The set is: that one image, the range `{x}…{y}`, or the whole folder. Wrap at both ends (see §8).



### Out of scope (not v2.0)

- Fullscreen, zoom/pan, slideshow
- Session unlock (one password, then several commands)
- Stable IDs, a manifest, or a format version bump
- Recursive directory `add`, or storing a directory as its own object in the crivate folder
- Export / decrypt-to-file, on-disk thumbnails, a GUI

## 3. Tech stack and architecture

Same as v1.0: C++17, MSVC, CMake, one x64 console `crivate.exe`, WIC, CNG, D3D11. Same source files. No new libraries.

`main.cpp` still owns argv, password prompts, and command dispatch.

`viewer.cpp` still owns the window and D3D. It must **not** call crypto. Next/prev is a callback from the viewer into `main` (see §8). Only the current image’s RGB is in memory.

Keep the derived folder key in memory for the whole `view` session. Wipe it when the window closes. v1.0 wiped the key before opening the window; that cannot stay if next/prev has to decrypt.

On-disk layout and formats are v1.0 (`CRIVATE1` / `CRI1`, same limits, same AAD). `password` writes the same `.crivate` layout with a **new** salt, nonce, tag, and verifier ciphertext, and the same `kdf_iters` value that was already stored in the file.

---



## 4. Indices and names

Unchanged from v1.0:

1. All cwd files whose name ends with `.cri` (case-insensitive).
2. Sorted with `CompareStringOrdinal` ignore-case.
3. Index `1` is the first in that list.

Adding or deleting can change later indices. `list` is how the user sees the current mapping.

Ranges `{x} {y}` are **1-based and inclusive**. `{x}` must be `<= {y}`. Do not swap them. `view 3 3` and `del 3 3` are valid and mean the single index 3.

Build the name list **once** after unlock, then use that snapshot for the rest of the command (the view set, or the delete list). Do not re-scan in the middle of `view` or `del`.

---



## 5. CLI behavior (exact)

General rules from v1.0 still apply: cwd only; unknown command or bad argc → usage, exit `2`; operational errors → stderr, exit `1`; success → exit `0`.

Usage text (keep short):

```
crivate init
crivate add <image-path> [image-path ...]
crivate count
crivate list
crivate view
crivate view <index>
crivate view <first> <last>
crivate del
crivate del <index>
crivate del <first> <last>
crivate password

Indices are 1-based from the sorted .cri names in this folder.
Adding or deleting an image can change later indices.
A directory passed to add contributes the image files directly inside it, not nested folders.
```

`view` with 4+ args, `del` with 4+ args, `list`/`password`/`count` with extra args, `add` with no paths → usage, exit `2`. Non-numeric index tokens → usage, exit `2`.

### `list`

Unlock, then list. Zero images is success: print `There are no images in the folder.` on stdout, exit `0`.

Each line on stdout:

```
<index><two spaces><basename>
```

Example:

```
1  Holiday.cri
2  other.cri
```

### `add` (one or more paths)

`argc >= 3`. Unlock once, then process arguments **in order**.

An argument is either a file or a directory. Directories are **not** stored as directories. Each image file found is added the same way as `crivate add that-file`: dest name is `{basename}.cri` in the crivate cwd (the source folder’s name is not part of the dest name).

**If the argument is a file:** use the per-file table below.

**If the argument is a directory:**

The directory is scanned for **image files**. An image file is a non-directory file whose name ends with one of these extensions (case-insensitive):

```
.png  .jpg  .jpeg  .bmp  .gif  .tif  .tiff  .webp
```

Match the suffix after the last `.` only (`Holiday.JPG` counts; `Holiday.jpg.bak` does not).

- Look only **directly** in that directory. Do not recurse.
- Every subdirectory is skipped (not an error).
- Every file that is not an image file (wrong or missing extension) is skipped (not an error).
- Sort the image files that remain with `CompareStringOrdinal` ignore-case (same order as `.cri` listing).
- Then run the per-file table on each, as if the user had passed those files to `add`.
- Directory with no image files: warning, not a hard error.
- Directory missing or not listable: hard error for that argument; continue with the rest.

This is not a new command and does not create a directory inside the crivate folder.

**Per-file table** (file arguments, and image files found in a directory):


| Situation                            | Result                                                              |
| ------------------------------------ | ------------------------------------------------------------------- |
| Dest `{basename}.cri` already exists | Skip. Print a warning on stderr. Not an error. Continue.            |
| Path missing / I/O / too large       | Print an error for **that** path on stderr. Continue with the rest. |
| WIC cannot decode the file           | Print an error for **that** path on stderr. Continue with the rest. |
| Encrypted and written                | Same success `INFO` line as v1.0. Continue.                         |


The source files are never deleted or moved. Existing `.cri` files are never overwritten. Two sources that share a basename: the first may add; the later one skips.

Exit `0` if every argument was added or skipped. Exit `1` if any argument had a hard failure, even if others succeeded.

### `view` / `view {x}` / `view {x} {y}`


| Situation                               | Result                                         |
| --------------------------------------- | ---------------------------------------------- |
| Folder has 0 images                     | Error, no window                               |
| `{x}` or `{y}` `< 1` or `> count`       | Error, no window                               |
| `{x} > {y}`                             | Error, no window                               |
| First image in the set fails to decrypt | Error, no window                               |
| Later image in the set fails on A/D     | Error on stderr; **stay** on the current image |


`view` blocks until the window closes.

### `del` / `del {x}` / `del {x} {y}`

Every `del` **always confirms**, including a single index. Order:

1. Require a crivate folder.
2. Unlock (password). Wrong password → error, **no** confirm prompt, nothing deleted.
3. Snapshot `.cri` names. Check the index or range with the same rules as `view` (`{x}` / `{y}` in range, `{x} <= {y}`). Zero images, or an empty selection, → error `There are no images in the folder.` or out-of-range as appropriate; **no** confirm; exit `1`.
4. Prompt on stderr (echo **on**, this is not a password). One line, then read one reply:

  | Command         | Prompt                                                           |
  | --------------- | ---------------------------------------------------------------- |
  | `del {x}`       | `Delete image {x} ({basename})? Type YES to confirm:`            |
  | `del {x} {y}`   | `Delete images {x} through {y} (N images)? Type YES to confirm:` |
  | `del` (no args) | `Delete all N images? Type YES to confirm:`                      |

   `{basename}` is the snapshot name for that index. `N` is how many `.cri` files this command would remove. For `del {x} {x}` use the single-image prompt, not the range prompt.
5. Confirm only if the line is exactly `YES` (three uppercase letters, no extra spaces). `yes`, `y`, `Yes`, empty, EOF → print an error, delete nothing, exit `1`.
6. Delete the snapshot basenames for this command only. Do not re-scan indices after each unlink. `.crivate` is never deleted. If a delete fails, stop, exit `1`. Files already removed stay removed.

`del {x} {y}` with `{x} > {y}` is an error before the confirm prompt (same as `view`).

### `password`

Order:

1. Require a crivate folder.
2. Prompt `Password:` (current). Unlock. Failure → nothing written.
3. Prompt `New password:` then `Confirm password:` (same empty / mismatch rules as `init`). Failure → nothing written.
4. Re-encrypt as in §7. Success → exit `0` and print nothing (or a single `INFO` line on stderr; either is fine, be consistent with `add`/`del`).

A new password equal to the old one is allowed (still re-salts and re-encrypts).

## 6. Confirmation and password prompts

Password prompts are unchanged from v1.0 (stderr, echo off, UTF-8, empty refused).

Every `del` confirmation is a normal echoed line on stderr. Restore console echo if you touched the mode; by default you should not disable echo for this prompt.

---



## 7. `password` (re-encrypt)

Same crypto as v1.0: PBKDF2-HMAC-SHA256, AES-256-GCM, unique 12-byte nonce per file, same AAD rules.

Do this in two phases so a failure **before** the replace phase leaves the folder as it was.

**Phase 1 — write temps only**

- Read `kdf_iters` and derive the **old** key from the current `.crivate` (already done by unlock).
- Generate a new 16-byte salt. Derive the **new** key from the new password + new salt, same `kdf_iters`.
- Snapshot the `.cri` list.
- For each `.cri`: decrypt with the old key (full v1.0 validation); encrypt with the new key to a **new** temp file in cwd (same atomic-write recipe as v1.0 `add`, name must **not** end in `.cri`). Remember `(temp, dest)` pairs. Wipe that image’s RGB before the next file.
- Build a new `.crivate` header in memory (new salt / nonce / tag / verifier ciphertext; same magic, version `1`, same `kdf_iters`). Write it to a temp file in cwd. Do not touch the real `.crivate` yet.

If anything in phase 1 fails: delete every temp created in this command, leave originals and `.crivate` unchanged, exit `1`.

**Phase 2 — replace**

- Rename each original `.cri` to a temp in the same directory (the name must not end in `.cri`). If any of those renames fails, rename the parked files back, delete the phase 1 temps, and leave the folder on the old password.
- Move each new image temp onto its `.cri` name. The previous ciphertext is still the parked file.
- Replace `.crivate` with its temp only after every image rename has succeeded.
- Delete the parked originals only after that replace succeeds.

If a rename fails before that delete, put the parked images back and exit `1`. The folder still opens with the old password, and the new temps are removed. If a parked file cannot be moved back, leave it in place and tell the user to put that file back under its `.cri` name, then run `password` again. Do not interrupt `password`. A crash can still leave temps behind, but it must not discard the only copy of an image.

Zero images: skip the `.cri` loop; still write a new `.crivate` via temp + replace (phase 1 temp for the header, then phase 2).

Wipe both keys when `password` returns.

`cri_write` in v1.0 refuses to overwrite. Do not use it as-is for the replace. Reuse encrypt + temp write; the replace step is `password`-specific.

## 8. Viewer (next / prev / wrap)

v1.0 drawing, window title `crivate`, no menu, `W` / `S`, 100 draws, `Present(1, 0)`, `Esc` / close box: unchanged.

### Current set

After unlock, `main` builds a vector of `.cri` basenames for this invocation only:

- `view {x}` → one name
- `view {x} {y}` → names from index `{x}` through `{y}` inclusive
- `view` → all names, in list order

Call that vector the **set**. Position `i` is `0 … set.size()-1`.

### Wrap

Let `n = set.size()` (`n >= 1` or the window never opens).

```
next: i = (i + 1) % n
prev: i = (i + n - 1) % n
```

If `n == 1`, next and prev leave `i` unchanged: treat as a no-op (do not reload, do not flash).

Wrap is only inside the set. `view 2 4` never shows image 1.

### Switching image

Keep **one** window and the existing D3D device. Do not destroy the window on A/D.

On a real switch (new `i`):

1. Decrypt `set[i]` with the folder key still held in `main`.
2. If decrypt fails: print the usual stderr error, keep the old RGB and grid, leave `i` where it was.
3. If decrypt succeeds: wipe the previous RGB buffer, take the new one, set `N = width * height` for **this** image (do not carry `W`/`S` from the previous picture), rebuild the grid, letterbox into the **existing** client area.

The window size is chosen once from the **first** image, same 80% work-area fit as v1.0. Later images letterbox in that client rect. Different aspects are fine. Do not resize the window.

### Keys

On key down, ignore auto-repeat (same bit as v1.0 `W`/`S`):

- `W` / `S` — existing square-count behavior, for the image on screen
- `A` or `VK_LEFT` — previous
- `D` or `VK_RIGHT` — next
- `Esc` — exit the viewer



### Callback shape (so viewer stays crypto-free)

Something equivalent to:

```
// delta is -1 or +1. Return false to keep the current image
// (n == 1, or decrypt failed). On true, *out is the new packed RGB.
bool load_delta(void* user, int delta, uint32_t* width, uint32_t* height,
                const uint8_t** rgb, size_t* rgb_len);
```

`main` owns `user` (key, set, `i`, RGB storage). `viewer_show` for a single image can pass this same callback; `n == 1` makes A/D a no-op.

When the viewer returns, `main` wipes RGB and the key.

## 9. Implementation order

Each phase should leave a runnable EXE.

### Phase A — `list` and usage

- Dispatch `list`; print lines as in §5.
- Update usage text for all v2.0 commands (even if some still error until later phases).

**Check:** folder with three `.cri` files → `list` shows `1` / `2` / `3` with the right names, sorted as v1.0. Empty folder → no lines, exit `0`. Wrong password fails. Extra args → exit `2`.

### Phase B — `add` several paths and directories

- Allow `argc >= 3`.
- One unlock; skip existing dest; continue after a bad path; expand directories as in §5.

**Check:** `add a.png b.jpg`; both appear. `add a.png` again skips, does not overwrite, exit `0`. `add missing.png good.jpg` errors on the missing one, still adds `good.jpg` if that dest is free, exit `1`. `add C:\pics` where `pics` has two JPEGs, a `.txt` file, and a nested folder: both JPEGs are added; the `.txt` and the nested folder are skipped.

### Phase C — `del` with confirmation

- `del {x}`, `del {x} {y}`, and `del` all share one confirm helper (exact `YES`).
- Wrong password, bad range, or `yes` / empty: nothing deleted.

**Check:** three images, `del 2 3` then `YES` leaves image 1 as index 1. `del 1` then `yes` leaves that image. `del` then `YES` leaves only `.crivate`. `count` is `0`.

### Phase D — `view` set + wrap

- Parse `view`, `view {x}`, `view {x} {y}`.
- Keep the key for the session. Callback for A/D. Wrap. Reset `N` on switch. Letterbox in the first window size.
- Decrypt failure on switch stays on the current image.

**Check:** `view` with three images; D from last shows the first; A from first shows the last. `view 2 3` never shows image 1. `view 1` A/D does not reload. `Esc` returns to the console. No new `.png` / `.bmp` in the folder. `W` / `S` still work. Still 100 draws per frame.

### Phase E — `password`

- Two-phase temps as in §7. Zero-image folder still gets a new `.crivate`.

**Check:** add two images, `password`, old password fails on `list`, new password `view`s both. If phase 1 fails, or a phase 2 rename fails and the originals can be put back, the folder still opens with the old password. New password empty or mismatch writes nothing.

### Phase F — polish

- Usage and the error table match §5.
- Wipe keys and RGB on every path, including failed `password` and failed next-image decrypt.

## 10. Testing (manual is enough)

Walk this list on top of the v1.0 checks (those must still pass):

1. Three images → `list` matches sorted names; `count` still has the label and `3`.
2. `add a.png b.jpg c.png` with one dest already present: that one skipped, others added. `add` a directory: only files with the image extensions in §5 are added, as `.cri` in the crivate folder (not a nested directory); other files and subdirectories in the source are skipped.
3. `view` then D through the end wraps to the first; A wraps the other way.
4. `view 2 3`: only those two; wrap stays inside `{2,3}`.
5. `view 5 2` errors. `view 0 1` errors. `del 9 9` errors.
6. `del` (no args), type `yes` → nothing deleted. Type `YES` → all `.cri` gone, `.crivate` remains, `list` is empty.
7. `del 1 2`, type `yes` → nothing deleted. Type `YES` → those two are gone. `del 1`, type `YES` → that one image is gone.
8. `password`; old password rejected; new password opens the same pictures.
9. Wrong password on `list` / `view` / `del` / `password` / multi-`add`: no changes.
10. After browsing several images, the folder still contains only `.crivate` and `.cri`.

---



## 11. Definition of done

v2.0 is complete when all of the following are true:

- One `crivate.exe` implements `list`, multi-`add` (files and non-recursive directory contents), `view` / `view {x}` / `view {x} {y}`, `del` / `del {x}` / `del {x} {y}`, and `password` as specified, and v1.0 commands still behave as in v1.0.
- No form of `del` can run without an exact `YES` after a successful unlock.
- Next/prev wraps inside the current set. One image in the set makes A/D a no-op.
- A wrong password cannot list, add, view, delete, or change the password.
- No decoded image pixels are written as an image file. The out-of-scope list in §2 is still out.

Nothing else is required to ship v2.0.
