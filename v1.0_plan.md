# crivate v1.0 — Implementation Plan

This is the plan for the first shippable version of crivate: a Windows console EXE that encrypts images into a folder and displays them privately. The application never intentionally persists decoded image pixels as an image file.

v1.0 does that loop and nothing else.

---

## 1. Goal

A user can:

1. Turn an empty folder into a crivate folder with a password.
2. Add an image; it is stored only as an encrypted `.cri` file.
3. Unlock the folder with that password and view an image on screen.
4. While viewing, change how coarsely the image is drawn (more / fewer colored squares).

If those four things work, v1.0 is done.

---

## 2. What v1.0 is — and is not

### In scope (the product)


| Command                    | Behavior                                                                         |
| -------------------------- | -------------------------------------------------------------------------------- |
| `crivate init`             | Initialize the **current working directory**. Prompt for a new password (twice). |
| `crivate add {IMAGE_PATH}` | Encrypt that image into the cwd as `{original_basename}.cri`.                    |
| `crivate count`            | Print how many `.cri` images are in the folder.                                  |
| `crivate view {x}`         | Open a window and show image **x** (1-based).                                    |
| `crivate del {x}`          | Delete image **x**.                                                              |


Every command except the password-setup half of `init` unlocks the folder with the password before doing work. `init` asks the user to **choose** a password.

Viewer (only while `view` is running):

- Decrypt pixels for display. Never intentionally persist decoded pixels as an image file (PNG/JPEG/BMP or otherwise).
- Draw the image as a grid of solid-color squares with Direct3D 11.
- Each square’s color is the average RGB of the image pixels it covers.
- Initial square count = pixel count of the image (`width * height`).
- `W` increases the **total** square count `N` by 20%; `S` decreases it by 20%.
  `N` stays in `[1, width * height]` (never finer than one square per pixel).
- Squares are issued in **exactly 100 draw calls** per frame (see §8).
- `Esc` closes the viewer and returns to the console.

### Out of scope (not v1.0)

These are real product ideas later, not this release:

- `view` with no args, `view {x} {y}`, `del` with no args, `del {x} {y}`
- Next/previous image in one session, slideshow, fullscreen, zoom/pan
- Changing the folder password, export/decrypt-to-file, thumbnails

`count` and single-index `del` stay in v1.0 because without them you cannot tell which index to `view` or remove a bad add without deleting the whole folder. Range/all variants are the extras.

## 3. Tech stack

Keep the binary self-contained. No package manager, no third-party libraries.


| Piece            | Choice                                                              | Why                                                              |
| ---------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Language         | C++17                                                               | Direct3D and Win32 without extra runtime                         |
| Compiler         | MSVC (Visual Studio 2022 or Build Tools)                            | Required for the Windows / D3D11 toolchain                       |
| Build            | CMake 3.20+ generating an MSVC solution, **or** a single `.vcxproj` | One `crivate.exe`                                                |
| Console + window | Console subsystem + a Win32 window only for `view`                  | Password stays in the terminal; the picture is a separate window |
| Images           | Windows Imaging Component (WIC)                                     | decode a source image file to packed RGB                         |
| Crypto           | Windows CNG (`bcrypt.h`)                                            | AES-256-GCM + PBKDF2, no extra crypto lib                        |
| GPU              | Direct3D 11                                                         | Matches “use DirectX”; D3D12 is extra complexity                 |


Target: **64-bit Windows 10/11**.

Subsystem: `CONSOLE`. `view` creates a standard overlapped window, pumps messages until `Esc` or the window is closed, then the process exits (or returns to `main` and exits).

## 4. Architecture

One EXE, no DLLs you ship. Logical modules (files, not a framework):

```
src/
  main.cpp          — argv, dispatch, cwd checks, password prompt
  folder.cpp/.h     — init marker, list/index .cri files, count, delete
  crypto.cpp/.h     — KDF, encrypt/decrypt, password verifier
  cri.cpp/.h        — .cri read/write, pixel buffer
  image_load.cpp/.h — WIC: file → tightly packed RGB8
  viewer.cpp/.h     — Win32 window, D3D11, grid, input, 100 draws
```

Data flow:

```
add:   IMAGE FILE  →  WIC RGB buffer  →  AES-GCM  →  *.cri on disk
view:  *.cri       →  AES-GCM         →  RGB buffer in process memory
                   →  CPU averages    →  instance buffer
                   →  D3D11 100 draws →  window
```

During viewing, decoded pixels may exist in application memory and graphics resources required for rendering. Wipe the derived key and plaintext RGB buffer when they are no longer needed (see §7).

## 5. Folder layout

A crivate folder contains:

```
<cwd>/
  .crivate          — folder marker + password verifier (not an image)
  photo.cri         — encrypted image (name comes from the source file)
  other.cri
```

Rules:

- The EXE must **not** live in this folder (documented; not enforced beyond a warning if `crivate.exe` is in cwd).
- The user must not hand-edit these files. The program is the only supported API.
- `init` is allowed only if the directory has **no** files (ignore `.` and `..` only). If anything is present, refuse.
- If `.crivate` is already there, `init` refuses.
- Every other command requires a readable `.crivate` in cwd; otherwise print an error and exit nonzero.

### Image indices

There is no extra manifest. The image list is:

1. All files in cwd whose name ends with `.cri` (case-insensitive).
2. Sorted with `CompareStringOrdinal` ignore-case (stable on Windows).
3. Index `1` is the first in that list.

Adding or deleting a file can change later indices. That is acceptable for v1.0. Document it in the `--help` text.

`add` writes `{basename}.cri` next to `.crivate`. Example: `crivate add C:\pics\Holiday.JPG` → `Holiday.cri`. If that name already exists, refuse (do not overwrite). The source file is **not** deleted or moved. Write the new `.cri` to a temporary file in the same directory, then atomically rename it to the final name only after the complete ciphertext has been successfully written (see §6.2).

## 6. On-disk formats

All multi-byte integers are **little-endian**.

### 6.1 `.crivate` (folder header)

```
Offset  Size  Field
0       8     magic: ASCII "CRIVATE1"
8       4     version: uint32 = 1
12      4     kdf_iters: uint32  (PBKDF2 iteration count, e.g. 600000)
16      16    salt: random 16 bytes
32      12    verifier_nonce: 12 bytes
44      16    verifier_tag: GCM tag
60      32    verifier_ciphertext: AES-256-GCM of 32 bytes of 0xA5
```

The 32-byte plaintext `0xA5…` is a canary. Decrypting it successfully means the password is right. It does **not** encrypt the images with a separate wrapping key; the same derived key encrypts every `.cri` in the folder (see §7).

### 6.2 `.cri` (one image)

```
Offset  Size  Field
0       4     magic: ASCII "CRI1"
4       4     version: uint32 = 1
8       4     width: uint32
12      4     height: uint32
16      12    nonce: 12 bytes (unique per file)
28      16    tag: GCM tag
44      N     ciphertext: AES-256-GCM of packed RGB
```

`N = width * height * 3`. Pixel layout of the plaintext:

- 8-bit channels, order **R, G, B**
- Row-major, top row first, no row padding
- No alpha (WIC conversion drops or composites alpha on white if needed)

Treat every `.cri` as untrusted input. Use these limits (same constants when `add` measures a source image):

```
MAX_WIDTH           = 16384
MAX_HEIGHT          = 16384
MAX_PIXELS          = 50000000
MAX_PLAINTEXT_BYTES = 150000000   // MAX_PIXELS * 3
CRI_HEADER_BYTES    = 44
```

**Read a `.cri` in this order, before allocating pixel or GPU buffers:**

1. If the file is shorter than `CRI_HEADER_BYTES`, reject.
2. Read the 44-byte header.
3. Reject if magic is not `CRI1` or version is not `1`.
4. Reject if `width == 0`, `height == 0`, `width > MAX_WIDTH`, or `height > MAX_HEIGHT`.
5. Compute `pixels` and `plaintext_bytes` with checked **64-bit** arithmetic (`uint64` width × height, then × 3). Reject on overflow.
6. Reject if `pixels > MAX_PIXELS` or `plaintext_bytes > MAX_PLAINTEXT_BYTES`.
7. Reject if the on-disk file size is not **exactly** `CRI_HEADER_BYTES + plaintext_bytes` (truncated files and extra bytes both fail).
8. Only then allocate, read the ciphertext, and decrypt.

**Atomic write:** create a temp file in the **same directory** as the destination (so the rename stays on one volume). Write the complete `.cri` (header + ciphertext). Close the handle. Rename to `{basename}.cri` (`MoveFileW` / `MoveFileExW`). If anything fails, delete the temp file and leave no truncated `{basename}.cri`.

## 7. Cryptography

### Key derivation

- Algorithm: **PBKDF2-HMAC-SHA256** via `BCryptDeriveKeyPBKDF2`
- Input: user password (UTF-8) + 16-byte salt from `.crivate`
- Output: 32-byte AES-256 key
- Iterations: stored in `.crivate` so you can raise them later without a format break; v1.0 writes `600000`

Do not store the password. Do not use a fixed salt.

### Encryption

- **AES-256-GCM** (`BCRYPT_AES_ALGORITHM` + GCM chaining)
- 12-byte random nonce per `.cri` and for the folder verifier (`BCryptGenRandom`)
- AAD: for `.cri`, bind the metadata needed to interpret the image: **magic, version, width, and height** (the 16 bytes at offset 0). A truncated, resized, or header-tampered file must fail auth.
- For `.crivate`, AAD can be the magic + version + kdf_iters + salt

Wrong password or bit-flipped ciphertext → GCM fail → message like `wrong password or corrupted file` (do not distinguish those two in the text; it leaks less).

### Password UX

- Prompt on stderr: `Password:` 
- Disable console echo (`ENABLE_ECHO_INPUT` off), read a line, restore echo, print a newline
- UTF-8: accept the console input as-is; hash the bytes you received
- `init`: prompt `Password:` then `Confirm password:`; mismatch → abort, write nothing
- Empty password → refuse

Overwrite the derived key when it is no longer needed (end of every command that unlocked the folder). Overwrite the plaintext RGB buffer when it is no longer needed (`add` after the `.cri` is written; `view` when the window closes). Best-effort; this is not a hardened enclave. Do not treat GPU/driver memory as wiped.

## 8. Viewer and rendering

This is the part that makes crivate what it is. Implement it as specified, not as a textured quad.

### Window

- Title: `crivate`
- Client area: fit the image aspect ratio, largest size that fits the work area minus a margin (e.g. 80% of the monitor). Letterbox in the window if the user resizes; v1.0 can ignore resize (fixed size at creation) to save time.
- No menu. Close box and `Esc` both exit the viewer.

### Grid

Let `W` × `H` be the image size in pixels. Let `N` be the target square count.

- On open: `N = W * H` (use 64-bit for the product, then clamp to a `uint32` you actually allocate).
- `N` is the **total** target square count (area), not the number of squares along one side.
- Delta is `max(1, N * 20 / 100)` — 20% of current `N` (at least 1 when `N < 5`).
- `W` key: `N = min(W * H, N + delta)`  (20% up; never above one square per pixel)
- `S` key: `N = max(1, N - delta)`  (20% down; can still reach 1)

Turn `N` into a grid that matches the image aspect, so that when `N == W * H` you get **one square per pixel**:

```
cols = max(1, round(sqrt(N * W / H)))
rows = max(1, round(N / cols))
```

Use `cols * rows` as the actual square count drawn. When `N == W * H` this yields `cols == W`, `rows == H`.

Square `(c, r)` (0-based) covers the half-open pixel rectangle:

```
x0 = c * W / cols     x1 = (c+1) * W / cols
y0 = r * H / rows     y1 = (r+1) * H / rows
```

All divisions integer. If a cell is empty (can happen at tiny `cols`), skip it or give it a 1×1 fallback so every cell has at least one pixel.

**Color:** average of all pixels in `[x0, x1) × [y0, y1)`, computed in 32-bit or 64-bit accumulators, then `uint8`. Recompute whenever `N` changes.

### GPU representation

- One unit quad in a vertex buffer (two triangles).
- One **instance** per square: clip-space (or pixel) position, size, RGB.
- Map instances into the client area so the full grid covers the image rectangle (preserve aspect, center).

Rebuild the instance buffer when `N` changes. If allocation fails, print an error and close the viewer.

### Exactly 100 draw calls

Every frame:

1. `Clear` the render target (black).
2. Split the instance list into **100** contiguous ranges, as even as possible (`base = i * count / 100`, `end = (i+1) * count / 100`).
3. Issue **100** `DrawIndexedInstanced` (or `DrawInstanced`) calls, including ranges of length 0 if there are fewer than 100 squares.

Do **not** collapse those into one draw. Do **not** draw the image as a single textured triangle. The 100 batches are part of the v1.0 behavior.

### Frame loop

- Standard Win32 loop: `PeekMessage` / `DispatchMessage`, then render.
- Handle `W` / `S` on key down (ignore auto-repeat flood if it makes `N` jump too fast; one step per distinct key-down is enough).
- `Esc` or `WM_CLOSE`: release D3D resources, wipe pixel buffer, destroy window, return to `main`.

No vsync requirement beyond `Present(1, 0)` so the window does not spin a core.

## 9. CLI behavior (exact)

General:

- Operate on **cwd**, not on a path argument.
- Unknown command or bad argc → print usage, exit `2`.
- Operational errors (bad password, missing file, I/O) → message on stderr, exit `1`.
- Success → exit `0`. `count` prints a single integer and a newline on stdout.

Usage text (keep short):

```
crivate init
crivate add <image-path>
crivate count
crivate view <index>
crivate del <index>
```


| Situation                                         | Result                                                 |
| ------------------------------------------------- | ------------------------------------------------------ |
| `init` in non-empty dir                           | Error, no files written                                |
| `init` when `.crivate` exists                     | Error                                                  |
| Command other than `init` without `.crivate`      | Error: not a crivate folder                            |
| Wrong password                                    | Error, no changes                                      |
| `add` path missing or not an image WIC can decode | Error                                                  |
| `add` would overwrite an existing `.cri`          | Error                                                  |
| `view`/`del` index `< 1` or `> count`             | Error                                                  |
| `view` with 0 images                              | Error                                                  |
| `del` last image                                  | Allowed; folder stays initialized (`.crivate` remains) |


`view` blocks until the window closes. Other commands print nothing on success except `count`.

## 10. Implementation order

Do these in order. Each step should leave something you can run.

### Phase A — Skeleton

- CMake (or vcxproj): `crivate.exe`, x64, Unicode, console subsystem.
- Link: `d3d11.lib`, `dxgi.lib`, `windowscodecs.lib`, `bcrypt.lib`, `user32.lib`, `gdi32.lib`.
- `main`: parse argv, print usage, `init` stub that creates `.crivate` with dummy bytes.

**Check:** `cmake --build` produces `crivate.exe`; `crivate` with no args prints usage.

### Phase B — Folder + password

- Random salt, PBKDF2, AES-GCM verifier as in §6.1.
- Hidden password prompt + confirm on `init`.
- `require_folder()` + `unlock(password)` used by later commands.
- `count`: list `.cri`, print length (works even with zero images).

**Check:** `init` in an empty dir; second `init` fails; `count` prints `0`; wrong password on `count` fails.

### Phase C — Add (encrypt)

- WIC load → packed RGB8 + width/height; apply the same dimension/pixel/byte limits as §6.2.
- Write `.cri` as in §6.2 (temp file in cwd, then atomic rename). Wipe the RGB buffer and key after success or failure.

**Check:** `add` a small PNG and a JPEG. Hex-inspect the `.cri`: magic `CRI1`, size **exactly** header + `w*h*3`. Original files unchanged. Folder listing shows the `.cri`. `count` is `1`. No leftover `.tmp` files.

### Phase D — Decrypt path (no window yet)

- Read `.cri` with the §6.2 validation sequence (header first, limits, exact size, then decrypt).
- Do not add a “save as PNG” helper, even for debugging.

**Check:** decrypt of a file you just added succeeds; flipping one ciphertext byte fails auth. Truncated file, extra trailing bytes, bad magic/version, width/height 0, dimensions over the maxima, `width*height` that would overflow the size math, and a truncated header all reject **before** a huge allocation.

### Phase E — Viewer, one square per pixel

- Win32 window + D3D11 device, swap chain, rasterizer with no culling, simple VS/PS (passthrough instance color).
- Build instance grid with `cols = W`, `rows = H` (ignore `W`/`S` for this phase).
- Average is trivial (one pixel per square).
- 100 instanced draws per frame as in §8.
- `Esc` closes.

**Check:** `view 1` shows the photo, recognizable. Process Explorer / your own code: no new image files in the folder or `%TEMP%`.

### Phase F — Variable square count

- `W` / `S` adjust `N`, rebuild grid and averages, re-upload instances.
- Confirm `N = W*H` at start looks like the photo, `S` repeatedly becomes blocky, `W` refines again up to `W*H`.

**Check:** hold the behavior in §8; always 100 draw calls (PIX or a frame counter in debug builds).

### Phase G — `del` and hardening

- `del {x}` removes that `.cri` only.
- Wipe the derived key and plaintext RGB buffer when they are no longer needed.
- Handle `E_OUTOFMEMORY` from D3D.
- Help text and the error table in §9.

**Check:** add three images, `view 2`, `del 1`, `count` is 2, former index 2 is now 1.

## 11. Testing (manual is enough for v1.0)

No test framework required. Walk this list before calling it done:

1. Empty folder → `init` → confirm password mismatch writes nothing.
2. `add` PNG, `add` JPEG, `count` is 2.
3. `view 1` and `view 2` show the right pictures.
4. Wrong password on `view` / `add` / `del` / `count`.
5. `view 0`, `view 99`, `del 99` error.
6. `del 1` then indices shift; remaining image still opens.
7. `W` / `S` change blockiness; `Esc` returns to a working prompt.
8. After `view`, the folder still contains only `.crivate` and `.cri` (no `.png` / `.bmp` dumps).
9. `init` in a folder that already has a file fails.
10. `add` of the same basename twice fails.
11. `view` of a truncated `.cri`, a `.cri` with extra trailing bytes, a corrupted header (bad magic or version), a header with enormous width/height, a header whose size math overflows, and a file with a corrupted GCM tag: all fail; no crash, no huge allocation.
12. Kill `add` conceptually (or inspect): a failed write must not leave a partial `{basename}.cri`; a leftover temp file is deleted or is not a valid `.cri`.

## 12. Definition of done

v1.0 is complete when all of the following are true:

- A single `crivate.exe` implements `init`, `add`, `count`, `view {x}`, `del {x}` as specified.
- The application never intentionally persists decoded image pixels as an image file. During viewing, decoded pixels may exist in application memory and graphics resources required for rendering.
- The on-screen image is a grid of averaged color squares, starting at one square per pixel, adjustable with `W` / `S`, drawn with 100 draw calls per frame.
- A wrong password cannot add, list-as-unlocked, view, or delete.
- The out-of-scope list in §2 is still out: no range commands, no decrypt-to-file.

Nothing else is required to ship v1.0.
